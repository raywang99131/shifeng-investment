# ETF 成交额异动监控重建设计

## 背景与根因

“拥挤度追踪”中的“ETF 成交额异动”目前只在主站内保留了前端卡片和 Express 代理。实际行情抓取、异动检测、SQLite 缓存与后台轮询仍依赖仓库之外的一套 FastAPI 服务，默认地址为 `http://127.0.0.1:8000`。

现场检查确认：

- 主站 `3000` 端口健康，但本机 `8000` 端口没有服务，主站 `/api/etf-monitor/overview` 因而返回 `503`。
- 主站代理调用 `/api/monitor/cached-snapshot`，而参考项目没有该接口；即使启动参考后端，各 ETF 快照仍会因 `404` 降级。
- 参考项目的调度器启动后全天轮询，没有区分交易日、午休和收盘后时段。
- 主站的生产构建和 Docker 配置没有包含参考项目，因此重新部署主站也不会自动恢复 ETF 后台。

本次重建以用户提供的 `/Users/ray_wang/Downloads/汇总代码库/3: etf_monitor/` 为行为参考，把可维护的 ETF 监控后端纳入主仓库和主站启动链路，不继续依赖 Downloads 或 Desktop 中的外部目录。

## 目标

1. “ETF 成交额异动”在主站内稳定返回数据，不再因外部目录缺失而永久 `503`。
2. 保留参考项目的多 ETF、15/5 分钟 K 线、成交额放大检测、SQLite 缓存和告警记录能力。
3. ETF 后台随主站运行环境启动并保持可健康检查；行情轮询只在 A 股交易时段运行。
4. 交易日上午 `09:30–11:30`、下午 `13:00–15:00` 自动轮询，午休和收盘后自动休眠；交易时段内启动服务时立即补轮询。
5. 页面读取只访问缓存，不因打开页面而对每个 ETF 重复抓取行情；“立即刷新”仍可显式触发一次全量轮询。
6. 行情源失败时展示最近缓存并标明降级原因，不能把旧数据标成实时数据。

## 非目标

- 不重做“拥挤度追踪”的其他指标。
- 不改变现有 ETF 异动阈值、15/5 分钟切换规则或邮件文案，除非测试证明参考实现存在明确错误。
- 不在本次工作中增加新的第三方付费行情源。
- 不自动修改真实 SMTP 密钥、Cloudflare Token 或其他本机秘密配置。

## 方案选择

采用“仓库内 Python ETF 服务 + Express 聚合代理”的方案。

保留 Python 的原因是参考实现已经覆盖 AkShare 数据适配、腾讯回退、混合周期 K 线、SQLite 去重和批量告警，直接迁移并修正边界风险最低。主站继续通过 Express 暴露统一的 `/api/etf-monitor/*`，前端无需直接感知第二个端口。

不把整套逻辑改写成 Node：当前主站没有等价的分钟行情、SQLite 和检测实现，重写会扩大范围并增加行为偏差。不继续读取外部参考目录：该目录不属于主站发布产物，路径变化或机器迁移都会再次导致同一故障。

## 代码与运行结构

### 仓库内 ETF 服务

参考项目中以下能力迁入主仓库的独立目录：

- 配置与监控标的解析；
- 行情抓取、AkShare/腾讯回退和 K 线标准化；
- 成交额异动检测；
- SQLite K 线、告警和通知去重；
- FastAPI 路由与健康状态；
- 交易时段感知的后台调度器；
- 对应的 Python 单元测试和依赖清单。

运行数据放在明确的持久化目录，代码发布不得覆盖数据库。默认本地数据库仍使用仓库内被 Git 忽略的数据路径；生产部署通过环境变量把数据库指向共享持久化目录。

### API 契约

ETF 服务提供：

- `GET /api/health`：进程、调度器阶段、数据状态、最近成功更新时间和最近错误；
- `GET /api/monitor/symbols`：配置中的监控标的；
- `GET /api/monitor/cached-snapshot?symbol=...`：只读 SQLite 缓存，不发起网络请求；
- `POST /api/monitor/poll-all`：显式轮询全部标的；
- `GET /api/alerts?symbol=...`：读取告警记录。

参考项目现有的 `GET /api/monitor/snapshot` 保留兼容，但主站概览只使用 `cached-snapshot`。这样页面每分钟刷新不会同时触发多只 ETF 的行情抓取。

Express 继续提供：

- `GET /api/etf-monitor/overview`：并发读取所有标的缓存和告警，再聚合为当前前端契约；
- `POST /api/etf-monitor/refresh`：先调用一次 `poll-all`，再返回新概览；
- `GET /api/etf-monitor/health`：透传并规范化 ETF 服务健康状态。

上游完全不可用时返回清晰的 `503`；只要至少一个标的存在可用缓存，概览可返回数据，同时把整体或单项状态标为 `cached/degraded`。

## 交易时段自动运行

ETF 服务进程随主站部署环境启动，但调度器采用状态机而不是全天无条件抓取：

- `pre_open`：交易日前 `09:30`，休眠；
- `morning_session`：`09:30–11:30`，按配置间隔轮询；
- `lunch_break`：`11:30–13:00`，休眠；
- `afternoon_session`：`13:00–15:00`，按配置间隔轮询；
- `post_close`：`15:00` 后停止行情轮询；已有日结逻辑只允许执行一次；
- `closed_day`：周末或确认的非交易日，休眠。

调度器使用 `Asia/Shanghai` 时间。第一版交易日判定按以下顺序：

1. 优先使用可注入、可缓存的 A 股交易日日历；
2. 日历刷新失败时沿用最近已缓存结果；
3. 没有任何日历数据时只把周一到周五作为降级候选，并在健康接口中明确显示日历降级，避免静默宣称“确认交易日”。

服务在交易时段内启动时立即轮询一次；之后使用基于停止事件的定时等待，使关闭进程无需等待完整轮询间隔。午休、收盘后和休市日不调用行情源，但仍能从缓存服务页面请求。

手动刷新属于显式用户操作，允许在非交易时段调用；如果行情源没有新 K 线，继续返回缓存而不生成重复告警。

## 启动与部署

### 本地及 Cloudflare Tunnel

现有 `scripts/cloudflare-tunnel.sh` 改为启动仓库内 ETF 服务，不再默认寻找 `$HOME/Desktop/etf_monitor`。脚本会：

1. 检查仓库内 Python 运行环境和依赖；
2. 启动 ETF 服务并等待健康检查；
3. 把 `ETF_MONITOR_URL` 传给 Node 主站；
4. 任一受管进程退出时输出明确日志并由外部 launchd/守护流程重启整套服务。

现有环境变量可以覆盖端口、Python 路径和数据库路径，但不再需要配置外部源码目录。

### Docker

Docker Compose 增加独立的 ETF 服务，API 服务通过内部网络访问它，并挂载持久化数据卷。API 服务依赖 ETF 服务健康后启动或在其暂时不可用时返回可诊断的降级状态。Python 依赖与 Node 镜像分离，避免让主 API 镜像承担两种运行时。

### 自动部署

仓库内 ETF 源码、依赖清单和启动脚本必须进入发布产物；SQLite 数据不进入版本化发布包。生产 launchd 仍可常驻启动整套平台，交易时段控制由 ETF 服务内部完成，而不是依靠脆弱的多条 launchd 分钟任务。

## 数据与告警正确性

- 快照只展示最新交易日的已完成 K 线。
- K 线以 `symbol + candle_time + kline_period` 唯一标识，避免 15 分钟与 5 分钟数据互相覆盖。
- 告警沿用参考项目的去重边界，不因后台重启、页面刷新或手动刷新重复写入。
- 当前告警仅在最新已完成 K 线确实对应一条告警时返回。
- 行情抓取失败不得更新“实时”时间戳；缓存时间与接口生成时间分开返回。
- 数据库迁移必须兼容参考项目现有 SQLite，测试迁移副本后再使用真实历史库。

## 错误处理与可观测性

健康接口至少区分：

- 进程是否健康；
- 调度器当前阶段以及是否正在轮询；
- 交易日日历是否确认或处于降级模式；
- 行情数据是 `live`、`cached`、`empty` 还是 `degraded`；
- 最近成功轮询时间、最近轮询尝试时间和最近错误。

一次 ETF 抓取失败不能阻止其他标的处理。后台异常记录到标准日志；页面保留已有缓存并展示简短错误，不输出 SMTP 密码或其他敏感配置。

## 测试策略

按测试驱动方式完成，重点覆盖：

1. 先建立当前代理与参考后端接口不匹配的失败测试；
2. 缓存快照不会调用行情客户端；
3. 概览能聚合实时、缓存和单项异常；
4. 交易日上午和下午会轮询，午休、收盘后、周末和已知休市日不会轮询；
5. 交易时段内启动会立即轮询，停止调度器能快速退出；
6. 手动刷新在非交易时段仍可显式执行；
7. 混合 15/5 分钟 K 线、成交额单位修正、异动阈值和告警去重保持参考行为；
8. SQLite 旧库迁移不会丢失 K 线或告警；
9. Cloudflare 启动脚本不再依赖外部源码目录；
10. Docker Compose 能正确注入 ETF 内部地址和持久化路径；
11. 主站 TypeScript 构建、ETF Python 测试及 Express API 测试全部通过。

实现后还会对本机实际链路做一次验证：ETF 健康接口可达、主站概览不再为 `503`、缓存快照可展示，并通过注入时间验证交易时段状态转换；不会为了测试等待真实开盘。

## 验收标准

- 不需要 Downloads/Desktop 中的参考文件夹，干净发布也能运行 ETF 监控。
- 主站 `/api/etf-monitor/overview` 在有缓存时返回 `200` 和非空标的列表。
- 交易时段内后台自动抓取；午休、收盘后和休市日不抓取。
- 行情源不可用时页面继续显示最近缓存，并准确标识降级状态和错误。
- 手动刷新、历史异动、图表和现有监控标的继续可用。
- 自动化测试、生产构建和启动链路验证通过。
